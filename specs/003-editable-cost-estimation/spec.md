# Feature Specification: Reliable AWS-MCP Generation with Attachable Services and Editable Cost Estimation

**Feature Branch**: `003-editable-cost-estimation`

**Status**: Draft

## Overview

The project-creation chat (feature 001, User Story 2) is unreliable and needs to be hardened, and
the flow it drives needs to be made explicit end-to-end: the assistant calls the **official AWS
MCP** to generate a base architecture from the user's prompt; the user can then **attach
additional services** to that existing architecture (rather than starting over); the system prices
the full architecture with the **official AWS cost MCP**; and the resulting **cost estimate becomes
editable** — the user can manually override specific, permitted fields of the estimate, and the
system immediately recalculates the total to reflect both computed and overridden values. This
feature extends feature 001's chat-based generation and cost engine and feature 002's canvas
editing; it does not replace them.

## Clarifications

### Session 2026-07-07

- Q: Does overriding a service's quantity/usage in the cost estimate also update that service's configuration on the architecture diagram? → A: No — cost-only, fully decoupled. The diagram stays purely visual and is never altered by a cost override. The cost estimate is a separate, independently editable artifact that can also be exported on its own (e.g. as a client-facing cost proposal), independent of diagram exports.
- Q: Can a line item have both a quantity/usage override and a flat total-cost override active at once? → A: Both allowed, quantity wins — a line item may carry both, but its quantity-derived price always takes precedence over any total-cost override for that line. The initial cost estimate is generated by the official AWS cost-estimation MCP; any later change — made either through a chat instruction or an inline edit — causes the full cost calculation to regenerate.
- Q: Should attaching a service update the diagram and the cost estimate as one combined step, or as a sequence? → A: Sequential, two distinct steps — the architecture (diagram) is generated or updated first; the cost calculation runs afterward, as its own step, against the resulting architecture. This ordering applies to both the initial generation and to attach actions, and each step (architecture and cost) can be independently modified afterward via a chat request.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Dependable architecture generation via AWS MCP (Priority: P1)

A user on the project-creation page describes their application and attaches the AWS tool. The
assistant reliably calls the official AWS MCP to produce a base architecture and the official AWS
cost MCP to price it — and when a call fails or times out, the user gets a clear explanation and a
retry, instead of the chat silently failing or hanging.

**Why this priority**: The current generation flow is unreliable; nothing else in this feature (or
in feature 001's core value proposition) matters if the base architecture cannot be dependably
produced in the first place.

**Independent Test**: Send a well-formed prompt with the AWS tool attached and confirm a costed,
editable architecture is returned within the expected time; separately, simulate an AWS MCP failure
and confirm the user sees a specific error and a working retry that does not lose their prompt.

**Acceptance Scenarios**:

1. **Given** the project-creation chat with the AWS tool attached, **When** the user sends a
   well-formed prompt, **Then** the assistant calls the official AWS MCP to generate the
   architecture and the official AWS cost MCP to price it, and returns an editable, costed diagram.
2. **Given** a prompt is submitted, **When** the AWS MCP or AWS cost MCP call fails or times out,
   **Then** the user sees which step failed and a retry action that resends the same prompt and
   attached context without requiring them to retype it.
3. **Given** a retry succeeds after a prior failure, **When** the architecture is returned, **Then**
   it replaces the failed attempt cleanly with no duplicate or partial services left behind.

---

### User Story 2 - Attach additional services to an existing architecture (Priority: P1)

After the base architecture exists, the user asks to add more services (e.g. "add a caching layer"
or "attach a CDN") or adds them from the catalog. The system extends the current architecture
in place — keeping everything already generated or edited — rather than regenerating it from
scratch.

**Why this priority**: Real designs grow incrementally; forcing a full regeneration to add one
service would destroy prior edits and is the second half of making the generation flow trustworthy.

**Independent Test**: Generate a base architecture, then request one additional service via chat
and add a second one directly from the catalog; confirm both appear alongside the untouched
original services, connections, and manual positions, and the cost estimate includes all of them.

**Acceptance Scenarios**:

1. **Given** an existing generated architecture, **When** the user asks the assistant to attach a
   specific additional service, **Then** the assistant adds it (with sensible default configuration
   and connections) without altering unrelated existing services, their configuration, or their
   positions.
2. **Given** an existing generated architecture, **When** the user adds a service directly from the
   catalog instead of through chat, **Then** it is merged into the same architecture and reflected
   in the assistant's context for subsequent messages.
3. **Given** a request to attach a service that already exists in the architecture, **When** it is
   processed, **Then** the system updates the existing service (e.g. quantity/configuration) instead
   of creating a duplicate.

---

### User Story 3 - Edit the generated cost estimate (Priority: P1)

Once an architecture (base plus any attached services) is priced, the user can manually adjust a
service's usage/quantity or replace its computed monthly cost with a fixed override value — for
example to reflect a negotiated discount — either by editing the cost line directly or by asking
the assistant in chat, and the architecture's total cost recalculates immediately to include the
change alongside all system-computed line items.

**Why this priority**: Official pricing rarely matches a customer's real negotiated rates or
planned usage exactly; without an editable estimate the tool's cost numbers are not trustworthy
enough to plan a budget around, which undermines the whole costing feature.

**Independent Test**: Generate and price an architecture, override one service's quantity and
another service's total cost with a fixed value, and confirm the architecture total updates
immediately to reflect both changes while all non-overridden services remain system-computed.

**Acceptance Scenarios**:

1. **Given** a priced architecture, **When** a user with edit access changes a service's
   usage/quantity, **Then** that service's line cost is recalculated from the pricing model using
   the new quantity and the architecture total updates immediately.
2. **Given** a priced architecture, **When** a user with edit access sets a fixed override value on
   a service's monthly cost, **Then** that line item shows the override value (clearly marked as
   manual) and the architecture total updates immediately to use it instead of the computed value.
3. **Given** a line item with an override, **When** the user resets it, **Then** the line reverts to
   the system-computed value and the total recalculates accordingly.
4. **Given** a line item with an override, **When** the underlying service's configuration
   subsequently changes, **Then** the override value is kept but the line item is visually flagged
   as possibly outdated until the user confirms or resets it.
5. **Given** a read-only collaborator viewing the estimate, **When** they view a cost line, **Then**
   they can see whether it is overridden but cannot set or clear an override.
6. **Given** an override input, **When** the user enters an invalid value (e.g. negative or
   non-numeric), **Then** the input is rejected with a specific message and the previous value
   remains in effect.
7. **Given** a priced architecture, **When** the user asks the assistant in chat to change a named
   service's usage/quantity or cost (e.g. "assume 3 instances instead of 2" or "set the EC2 cost to
   $200/month"), **Then** the assistant applies it as the same kind of override as an inline edit and
   the total recalculates immediately.
8. **Given** a line item that has both a quantity override and a total-cost override active, **When**
   the total is calculated, **Then** the quantity-derived price is used for that line, not the
   total-cost override.

---

### User Story 4 - Export the cost estimate as a client-ready proposal (Priority: P2)

Once an architecture is priced (with any manual overrides applied), the user can export the cost
estimate on its own — independent of the architecture diagram — as a shareable document suitable
for presenting to a client as a cost proposal.

**Why this priority**: Sharing costs with a client or stakeholder is a distinct need from sharing
the design itself; forcing recipients to open a diagram export to find the numbers that matter to
them is friction the core override capability (US3) doesn't need in order to deliver value.

**Independent Test**: Price an architecture with one overridden line item, export the cost estimate
alone, and confirm the resulting document lists every line item (computed and overridden, clearly
marked) and the total, without requiring or including the diagram export.

**Acceptance Scenarios**:

1. **Given** a priced architecture, **When** the user exports the cost estimate (as opposed to
   exporting the diagram), **Then** a standalone document is produced containing the cost breakdown
   (per-service and total, monthly and annual) in a share-ready format.
2. **Given** an architecture with both overridden and computed line items, **When** the estimate is
   exported, **Then** overridden line items are clearly marked as manual in the exported document,
   consistent with how they appear on-screen.
3. **Given** a user who wants both artifacts, **When** they export the diagram and the cost estimate
   separately, **Then** each export succeeds independently and neither includes the other's content
   by default.

---

### Edge Cases

- **AWS MCP or AWS cost MCP unavailable during an attach request**: the existing architecture is
  left untouched, and the user sees the same failure/retry treatment as initial generation (US1).
- **Attaching a duplicate service**: merged into the existing line (quantity/config updated) instead
  of creating a second entry (US2, scenario 3).
- **Overridden line item's service is later removed**: the override is discarded along with the
  line item; no orphaned override remains.
- **Concurrent chat-driven update and manual override on the same service**: the latest completed
  action wins and the user is shown the reconciled value, consistent with feature 001's
  direct-edit-vs-pending-generation rule.
- **All line items overridden**: the architecture total is still computable and clearly reflects
  that every component is a manual value.
- **Override attempted by a user without edit access**: refused, consistent with the project's
  existing sharing/permission model.
- **Exporting the estimate while a line item is flagged as possibly outdated**: the export includes
  that flag so recipients of the proposal know the figure needs confirmation, rather than presenting
  it as a settled number.
- **Ambiguous chat cost-change instruction**: if the assistant cannot tell which service or which
  field (quantity vs total cost) the user means, it asks a clarifying question instead of guessing
  or applying no change.

## Requirements *(mandatory)*

### Functional Requirements

**Reliable generation**

- **FR-001**: The system MUST generate the initial architecture for a project as two sequential
  steps: first calling the official AWS MCP with the user's prompt to produce the architecture
  (diagram, services, connections), then calling the official AWS cost MCP against that resulting
  architecture to produce its cost estimate, per feature 001 FR-014b/FR-019. The architecture step
  MUST complete and be shown before the cost step runs.
- **FR-002**: When an AWS MCP or AWS cost MCP call fails or times out, the system MUST tell the user
  which step failed and offer a retry that reuses the original prompt and attached context, without
  discarding any architecture that existed before the failed call.
- **FR-003**: A successful retry MUST cleanly replace the failed attempt's output, leaving no
  duplicate or partially-created services, connections, or cost lines.

**Attaching services to an existing architecture**

- **FR-004**: Users MUST be able to attach additional services to an already-generated architecture,
  either via a follow-up chat request or by adding a service directly from the catalog, without
  discarding or regenerating previously generated or edited services, connections, or positions
  (extends feature 001 FR-014d).
- **FR-005**: When an attach request targets a service that already exists in the architecture, the
  system MUST update the existing service (e.g. quantity or configuration) rather than create a
  duplicate.
- **FR-006**: Every attach action (chat-driven or catalog-driven) MUST follow the same two-step
  order as FR-001: the architecture is updated with the attached service first and shown to the
  user, then the full architecture is re-priced via the official AWS cost MCP as a following step.
  Both steps MUST update the assistant's context so subsequent chat messages see the current
  architecture and cost estimate.

**Editable cost estimation**

- **FR-007**: The system MUST compute a cost estimate for the full current architecture (base plus
  attached services) using the official AWS cost MCP, per feature 001 FR-019.
- **FR-008**: Users with edit access to the project MUST be able to override, per service line item,
  (a) the usage/quantity feeding the pricing model, and/or (b) the line item's total monthly cost as
  a fixed value; the underlying provider unit rate itself is not directly editable. A line item MAY
  carry both an active quantity override and an active total-cost override at once; when both are
  present, the quantity-derived price MUST take precedence over the total-cost override for that
  line's contribution to the total.
- **FR-008a**: Users MUST be able to set either override through either of two equivalent paths: an
  inline edit on the cost line item, or a chat instruction naming the service and the desired
  usage/quantity or cost. Both paths produce the same override record and the same immediate
  recalculation (FR-010). If a chat instruction to change a cost does not clearly identify which
  service or which field it targets, the assistant MUST ask for clarification rather than guessing.
- **FR-009**: The system MUST visually distinguish overridden line items from system-computed ones,
  and MUST let the user reset an overridden line item back to the system-computed value at any time.
- **FR-010**: The system MUST recalculate the architecture's total (monthly and annual) immediately
  whenever a line item is overridden, reset, or a service is attached/edited — combining computed
  and overridden line items in the same total.
- **FR-011**: The system MUST validate override input (numeric, non-negative, required) and reject
  invalid values with a specific message, leaving the prior value in effect.
- **FR-012**: When a service's configuration changes while its cost line has an active override, the
  system MUST keep the override value but flag the line item as possibly outdated until the user
  confirms or resets it.
- **FR-013**: Overrides MUST persist with the project's architecture and cost estimate across
  sessions, and MUST be discarded automatically if the line item's underlying service is removed.
- **FR-014**: Only users with edit access to the project may set or clear an override; users with
  read-only access may view override status but not change it, consistent with the project's
  existing sharing/permission model.
- **FR-015**: A cost override MUST NOT alter the corresponding service's configuration on the
  architecture diagram; the diagram remains a purely visual representation of the design, decoupled
  from and unaffected by cost-layer overrides.

**Exporting the estimate**

- **FR-016**: Users MUST be able to export the cost estimate — including any overrides, clearly
  marked as manual — independently of the architecture diagram, in a form suitable for sharing with
  a client as a cost proposal. This extends feature 001's export capability (FR-024) with an
  estimate-only export target.

### Key Entities *(include if feature involves data)*

- **CostEstimateOverride**: an edit-access user's manual override on one architecture cost line
  item — independently holding a quantity/usage override, a total-cost override, or both (with the
  quantity override taking price precedence when both are present); plus who set each value, when,
  how (inline edit or chat instruction), and whether the underlying computed value has since changed
  (the "possibly outdated" flag). Persists with the Architecture, separately from any diagram
  service configuration; cleared when its line item's service is removed.
- **GenerationAttempt**: a record of one AWS-MCP-backed generation or pricing call (initial or
  attach-triggered), its status (succeeded/failed/retried), and, on failure, which step failed —
  used to drive the retry experience and prevent duplicate/partial output.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: At least 99% of well-formed generation prompts with the AWS tool attached return a
  costed, editable architecture without the user needing to retry.
- **SC-002**: When a generation or attach call fails, 100% of failures show the user a specific
  reason and a working retry, with zero duplicate or partial services left in the architecture
  after a successful retry.
- **SC-003**: Attaching a service to an existing architecture never alters the position,
  configuration, or connections of an unrelated pre-existing service (100% preservation, matching
  feature 001 FR-014d).
- **SC-004**: A user can override a service's cost and see the architecture total reflect the new
  value in at most 2 actions (select the field, enter the value), with the update visible within 1
  second.
- **SC-005**: 100% of invalid override inputs are rejected with a specific, actionable message and
  produce no change to the architecture total.
- **SC-006**: Overrides remain intact and correctly flagged after reloading the project in a new
  session, matching the persistence guarantee of the base architecture.
- **SC-007**: The cost estimate can be exported without the architecture diagram in 100% of cases,
  and every exported line item correctly shows whether it is overridden or system-computed.

## Assumptions

- **Builds on feature 001** (chat-based generation, official AWS MCP / AWS cost MCP integration,
  per-project persistence and sharing model) and **feature 002** (canvas editing, direct
  service add/configure): this feature hardens the generation flow and adds override capability on
  top of them rather than replacing them.
- **MongoDB Atlas services are out of scope for override**: this feature's cost-override capability
  applies to AWS line items priced via the official AWS cost MCP; Atlas pricing overrides are future
  work unless the same mechanism is trivially reusable at implementation time.
- **"Permitted" override fields default to usage/quantity and a flat total-cost override per
  service line item**; no other estimate fields (e.g. the provider's underlying unit rate) are
  user-editable in this feature. Chosen because these two cover the realistic reasons a user
  overrides a cloud estimate (different planned usage, or a negotiated/contracted rate) without
  letting overrides silently corrupt the provider's own pricing data.
- **The cost estimate is a separate artifact from the architecture diagram**: overrides live only
  in the cost layer and never write back to a service's diagram configuration (per Clarifications),
  which is what makes the estimate independently editable and independently exportable as a
  client-facing proposal, distinct from feature 001's diagram-centric exports.
- **A stale override (config changed after the override was set) is kept and flagged**, not
  silently discarded or silently recalculated — consistent with feature 001's "preserve user work"
  principle (FR-014d), applied here to manual cost input instead of diagram edits.
- **Edit-access permission reuses the project's existing sharing model** from feature 001 (owner and
  any collaborator granted edit access); no new permission tier is introduced for overrides.
